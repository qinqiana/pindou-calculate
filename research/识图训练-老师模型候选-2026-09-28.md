## 0. 先纠正一个命名事实

**事实**：截至 2026-09-28，Hugging Face 的 Qwen 官方组织下**没有叫 "Qwen3.5-VL" 的模型仓库**。Qwen3.5 这一代本身就是统一多模态架构——官方模型卡写明 "Type: Causal Language Model with Vision Encoder"、"Unified Vision-Language Foundation"，HF 管线标签全部是 `image-text-to-text`（图片+文字进、文字出），模型架构类是 `Qwen3_5ForConditionalGeneration`（含 vision_config 视觉塔）。也就是说"Qwen3.5-VL 系列"实际就是 **Qwen3.5 全系**。社区有叫 `Qwen3.5VL-xxx` 的微调衍生（如 [twinblade02/Qwen3.5VL-0.8B-ImageExplainer-GGUF](https://huggingface.co/twinblade02/Qwen3.5VL-0.8B-ImageExplainer-GGUF)），不是官方命名。
来源：[Qwen/Qwen3.5-9B 模型卡](https://huggingface.co/Qwen/Qwen3.5-9B)、[config.json](https://huggingface.co/Qwen/Qwen3.5-9B/blob/main/config.json)、[HF 模型列表 API（author=Qwen, search=Qwen3.5）](https://huggingface.co/api/models?author=Qwen&search=Qwen3.5&limit=100)、官方博客 [Qwen3.5: Towards Native Multimodal Agents](https://qwen.ai/blog?id=qwen3.5)。

### 1.2 官方推荐的推理框架

**事实**（[9B 模型卡 Quickstart](https://huggingface.co/Qwen/Qwen3.5-9B)）：模型卡写明权重 "compatible with Hugging Face Transformers, vLLM, SGLang, KTransformers"，并明确"生产或高吞吐场景强烈推荐 SGLang、KTransformers 或 vLLM"；给出 SGLang / vLLM / KTransformers / transformers serve 四种启动示例。注意两点：

- transformers 也要求最新版；config.json 标注 `transformers_version: 4.57.0.dev0`。**本机 comfyui-env 已是 transformers 5.15.1**（本地查看结果），版本号远高于此，**推断**可加载 Qwen3.5，但未实测。

### 1.3 哪些能在本机（121GB 统一内存）跑起来

**推断**（方法：BF16 每参数 2 字节、FP8 1 字节、Int4 0.5 字节估算权重，再加 KV cache 与激活开销；本机 121GB 统一内存与 ComfyUI、llama.cpp 等常驻服务共用，建议至少留出 20–30GB 余量）：

| 模型 | BF16 权重估算 | FP8 / Int4 估算 | 结论 |
|---|---|---|---|
| 0.8B | ≈1.6GB | — | 轻松 |
| 2B | ≈4GB | — | 轻松 |
| 4B | ≈8GB | — | 轻松 |
| 9B | ≈18GB | Int4 ≈5GB | 轻松；GGUF 实据：unsloth 仓库 BF16 文件约 16.7GiB（[文件列表](https://huggingface.co/unsloth/Qwen3.5-9B-GGUF/tree/main)） |
| 27B | ≈54GB | FP8 ≈27GB / Int4 ≈14GB | 可行，BF16 也放得下 |
| 35B-A3B | ≈70GB | FP8 ≈35GB / Int4 ≈18GB | BF16 偏紧（与其他服务共用），量化版从容 |
| 122B-A10B | ≈244GB | FP8 ≈122GB / Int4 ≈61GB | BF16 不行；Int4 可行但吃紧；社区已在同机型跑通 Int4（见 §4） |
| 397B-A17B | ≈794GB | Int4 ≈200GB | 单机放不下，排除 |

权重体积的校准点（**事实**）：unsloth/Qwen3.5-9B-GGUF 的 GGUF 元数据 `total=8,953,803,264` 参数、BF16 主文件列表约 17.9GB，与"每参数 2 字节"估算一致。
标注场景的上下文很短（一图 + 几百 token 指令 + 几百 token 输出），KV cache 可按 8K 上下文预算，不需要模型卡默认的 262K，内存压力主要来自权重本身（**推断**）。

## 2. aarch64 Linux + CUDA 推理路径逐项核验

本机背景（**事实**，本地只读查看）：spark-5681，aarch64 + NVIDIA GB10（DGX Spark 类，SM121）；comfyui-env 有 torch 2.13.0+cu130、transformers 5.15.1、onnxruntime 1.29；`/home/kenbattle/apps/llama.cpp` 检出为 commit `eb25b72`（2026-08-25），**已编译 CUDA 后端**（build/bin 下有 libggml-cuda.so、libmtmd.so、llama-server）。沙箱内看不到 /dev/nvidia*，未做任何 GPU 实测。

### 2.1 transformers

**事实**：PyTorch 官方为 aarch64+CUDA 提供 wheel——vLLM 官方安装文档的预编译包命令里 `CPU_ARCH=$(uname -m) # x86_64 or aarch64`，并配 `--extra-index-url https://download.pytorch.org/whl/cu130`（[vLLM GPU 安装文档](https://docs.vllm.ai/en/stable/getting_started/installation/gpu/)）；PyTorch 官方博客有专文 [vLLM and PyTorch Work Together to Improve the Developer Experience on aarch64](https://pytorch.org/blog/vllm-and-pytorch-work-together-to-improve-the-developer-experience-on-aarch64/)。本机 torch 2.13.0+cu130 已装好（本地事实）。
**结论（推断）**：transformers 路径在本机大概率开箱可用，是门槛最低的试跑路径；缺点是吞吐最低，适合先验证正确性再换引擎。

### 2.2 vLLM

**事实**：官方发布提供 `manylinux_2_28_aarch64` 的 CUDA 预编译 wheel（同上 vLLM 安装文档）；官方文档有"Building vLLM's Docker Image from Source for Arm64/aarch64"专节，覆盖 GH200/GB200/GB300（Grace-Hopper / Grace-Blackwell）。Qwen3.5 模型卡给出 vLLM 启动命令并要求最新代码。
**注意（事实+推断）**：官方文档示例的 `torch_cuda_arch_list` 是 "9.0 10.0+PTX"，而 GB10 是 SM121；社区仓库 [jilycn/spark-vllm-122b](https://github.com/jilycn/spark-vllm-122b)（"vLLM Qwen3.5-122B NVFP4 on DGX Spark (SM121) — full Docker build with 15 patches"）说明在 DGX Spark/SM121 上社区需要打补丁自建。**推断**：vLLM 官方 wheel 在 GB10 上可能需要额外适配或直接用 PTX JIT；可用性概率高但有踩坑风险，试跑前预留排错时间。**未核实**：官方 wheel 在 SM121 上的实际表现。

### 2.3 MNN（Linux 侧）

**事实**：阿里 MNN 官方文档 [MNN-LLM 用户指南](https://mnn-docs.readthedocs.io/en/latest/transformers/llm.html) 给出 mac/linux/windows 的编译方法（`-DMNN_BUILD_LLM=ON`；图像/音频输入再加 `-DMNN_BUILD_LLM_OMNI=ON`）。官方模型出口 taobao-mnn 有 Qwen3.5 全系 MNN 版（[Qwen3.5-0.8B-MNN](https://huggingface.co/taobao-mnn/Qwen3.5-0.8B-MNN)、[Qwen3.5-9B-MNN](https://huggingface.co/taobao-mnn/Qwen3.5-9B-MNN) 等，均 apache-2.0），文件清单含 `visual.mnn` + `visual.mnn.weight`，即**包含视觉文件**。注意文档另有一句：GGUF 转 MNN 的转换路径"目前本方案不支持多模态的模型转换"，多模态要走 llmexport 从 HF 导出。
**结论（推断）**：MNN Linux 侧技术上可行，但需要本机自行编译 MNN 引擎，且 MNN 的主战场是端侧（Android/iOS）；老师模型在训练机上跑、不上手机，**用 MNN 当训练机标注引擎没有必要性**，列为不推荐路径。MNN 版权重的价值在于将来端侧（另一张票的事）。

### 2.4 llama.cpp（GGUF + mmproj）

**事实**：
- 本机 llama.cpp（eb25b72，2026-08-25）源码含 `src/models/qwen35.cpp` 与 `qwen35moe.cpp`，架构表注册 `qwen35`/`qwen35moe`（本地 grep 结果）；多模态侧 mtmd 的视觉投影只有 `qwen2vl`/`qwen3vl` 图，**没有单独的 qwen35 视觉图**（上游 master 的 [clip.cpp](https://github.com/ggml-org/llama.cpp/blob/master/tools/mtmd/clip.cpp) 同样如此）。
- 社区 GGUF 已带视觉投影文件：unsloth/Qwen3.5-9B-GGUF 文件列表含 `mmproj-BF16.gguf / mmproj-F16.gguf / mmproj-F32.gguf`（[文件列表](https://huggingface.co/unsloth/Qwen3.5-9B-GGUF/tree/main)）；bartowski、lmstudio-community 等有 27B/35B/4B/0.8B 等尺寸的 GGUF。Qwen 官方组织本身没有发 GGUF（HF API 核对）。
- 旁证：ollama issue [#15898](https://github.com/ollama/ollama/issues/15898) 写明"上游 ggml-org/llama.cpp 已支持 qwen35/qwen35moe 两种架构"，该 issue 的失败点是 ollama 自己 vendored 的旧副本，不是上游；标题即"挂 mmproj 时架构缺失"，说明上游挂 mmproj 的路径是通的。
**推断**：qwen35 的 mmproj 很可能复用 `qwen3vl_merger` 投影类型（mtmd 里没有别的候选），本机这份已编译 CUDA+mtmd 的 llama.cpp 有较大概率直接加载社区 GGUF+mmproj 跑 Qwen3.5 视觉。**未核实**：未实际加载过（不跑 GPU 任务的约束）；mmproj 内部的 projector 类型字符串未读取验证。

### 3.1 官方模型卡基准（事实，来源为各模型卡的 Vision Language 基准表）

**能输出边框坐标吗（事实+推断）**：RefCOCO 与 ScreenSpot 是必须预测目标框/点坐标才能得分的基准，全系都有分，说明 Qwen3.5 具备输出坐标定位的能力（事实层面）。Qwen3-VL 模型卡也明确写有 "2D grounding"（[Qwen3-VL-8B-Instruct 模型卡](https://huggingface.co/Qwen/Qwen3-VL-8B-Instruct)）。**推断**：让它以 JSON 输出"色号文字 + 数量 + 所在框"在能力边界内；但框的像素精度能否直接当检测标注（IoU 够不够高），模型卡没有答案，必须试跑实测。

### 3.2 对拼豆图例场景的适用性

**事实**：以上基准全是通用 OCR/文档/定位基准。**没有任何官方或一手资料直接评测过"拼豆图纸逐色数量图例"**（色号形如 C12/H7/M01、三类排版、MARD 221 色卡约束）。本文不提供编造数字。
**推断**（给出理由）：拼豆图例是"小字号短文本 + 色块与文字的版面对应 + 整数数量"，接近 OCRBench/OmniDocBench/CountBench 三者的组合，9B 在这三项都是 89+ 分档，零样本有可期待的下限；难点在"色号↔色块↔数量"三者的对应关系（尤其色号印在色块内、数量在下方那类排版），这更靠近版面/关系理解，误差风险主要在这里。0.8B 的 OCR 指标（尤其 CharXiv、CountBench 低档值）明显弱一截，**推断**不宜当老师，只适合做下限对照。
**少样本**：模型卡没有任何针对图纸图例的少样本数据（未核实/无证据）；是否需要微调由后续"老师标注试跑"实测决定，本票不下结论。

## 4. 标注 300 张图的耗时估算（全部为推断）

**估算方法**：总耗时 ≈ 300 ×（prefill 时间 + decode 时间）；prefill ≈ 输入 token 数 ÷ prefill 速度，decode ≈ 输出 token 数 ÷ decode 速度。

**输入 token（推断，有事实基础）**：视觉预处理 patch_size=16、merge_size=2（[preprocessor_config.json](https://huggingface.co/Qwen/Qwen3.5-9B/blob/main/preprocessor_config.json)），即约 32×32 像素 1 个图像 token。以真图样本 1080×1207（samples.json 中 S01）为例：(1080/32)×(1207/32) ≈ 34×38 ≈ **1,290 图像 token**，加指令与模板约 200 token，单图输入 ≈ 1,500 token。更大原图（如 5000×3820）会显著更多，试跑时应先把图缩到图例可读的最小尺寸。

**输出 token（推断）**：要求输出 221 色卡内出现色号的 JSON（色号+数量+框），一图一般几个到二三十个色，**非 thinking 模式**约 300–600 token；若开 thinking，思考链可能多出几千 token，标注场景建议关 thinking（模型卡支持 `enable_thinking: False`）。

**速度锚点（社区二手数据，非官方，标注为参考）**：[albond/DGX_Spark_Qwen3.5-122B-A10B-AR-INT4](https://github.com/albond/DGX_Spark_Qwen3.5-122B-A10B-AR-INT4/) 报告 DGX Spark 上 Qwen3.5-122B-A10B（Int4 混合量化、vLLM 0.19）基线 28.3 tok/s、优化后约 52 tok/s，README 徽章另给出 Qwen3.5-35B 约 112 tok/s。没有 9B 的 DGX Spark 实测（未核实）。

**估算（推断，假设：9B、decode 100–200 tok/s、prefill 1,000–3,000 tok/s、batch=1、关 thinking）**：

- 单图 prefill ≈ 1,500 ÷ 1,000–3,000 ≈ 0.5–1.5 秒；decode ≈ 450 ÷ 100–200 ≈ 2–4.5 秒；视觉编码器前处理另加约 1–3 秒（推断，无来源）。
- 单图合计约 **4–9 秒**；**300 张 ≈ 20–45 分钟**。保守（开 thinking、吞吐打折、与其他服务抢内存）按 3 倍计：**约 1–2 小时**。
- 换 27B（decode 推断 40–80 tok/s）：300 张约 **1–3 小时**。

结论（推断）：无论 9B 还是 27B，300 张标注都是"半天以内"量级，**吞吐不构成选型约束**，选型应按准确率（上限对照）而不是速度。

## 5. 推荐老师、备选与试跑先验证的三件事

**推荐老师：Qwen3.5-9B**（apache-2.0）。理由（基于上文事实+推断）：OCRBench 89.2 / OmniDocBench 87.7 / CountBench 97.2 / RefCOCO 89.7，在能轻松装进 121GB 的档位里指标最强；BF16 约 18GB，与常驻服务共存无压力；9B 是官方阵容里"小尺寸旗舰"定位（模型卡与 GPT-OSS-20B 等对照）。

**备选**：
1. **Qwen3.5-27B**（apache-2.0）——做"准确率上限对照"的加强版：各项指标再高一点，BF16 ≈54GB 仍可行，速度慢一档但不构成约束。
2. **Qwen3.5-35B-A3B**（MoE，apache-2.0）——激活仅约 3B，解码快、指标与 27B 同档；官方有 FP8/GPTQ-Int4。混合 DeltaNet+MoE 在各推理框架里踩坑面略大（推断）。
3. **Qwen3.5-0.8B** 只作下限参照物，不建议当老师（OCR/计数指标明显低，见 §3.1）。
