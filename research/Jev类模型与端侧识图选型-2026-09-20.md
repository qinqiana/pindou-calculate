# Jev 类模型与端侧识图选型

调查日期：2026-09-20。任务：为 Issue #8 核查近期 Jev 类模型能否在 Android 或微信小程序本地识别拼豆图纸，并与小型 OCR 比较。用户已澄清名称是 **Jev**。本文为资料调查与技术建议，不改根规格、不安装模型、不宣称通过算法或真机验收。

## 结论

**对当前规则拼豆图，应优先验证自动点阵定位与逐格统计，不先携带数百 MB 的视觉模型。** 用户指出轻量 App 的体积约束后，已回看实际图纸并完成无模型小实验：148 颗原图自动定位和匿名颜色分组计数成立，自动色号对应与跨版式仍未解决。详见下节。

此前优先建议 Tiny OCR，未先充分验证点阵路线，现予修正。下文模型资料作为候选调查保留，不表示接入决定。官方 Jev 当前不支持图片；本次核查到的社区视觉实现也不是几 MB 的手机识图替代品。小型字符模板、平台已有识字能力或小 OCR 模型，只在色号读取的实测需要明确后比较。

## 实际图纸检查与无模型实验

输入为仓内 18 张图纸与 1 张色卡，分组见 `experiments/issue8/samples.json`。只读取原图，在 `/tmp/pindou-issue8` 留存诊断脚本与结果；未安装或下载模型、未上传图片、未修改应用代码。现有点阵脚本依赖人工网格和代表格，本次新增临时探针验证自动定位，不把旧脚本成功当作自动成功。

方法是按 RGB 通道提取边缘、保留长直线、拟合等距网格，再分析每格底色与内部字迹。自动判断行列编号边框后，按底色聚类计数；所有颜色组的 `code` 均为空。算法不接收手工框、网格参数、色号或数量答案；参考数量只用于运行后的核对。低对比格不直接宣称为空白，所有输出均为待复核的诊断结果。

**148 颗开发样例：** 自动得到 29 列 × 16 行，148 个带字迹格、316 个低对比格，9 个匿名颜色组；按原图颜色人工对应图例复核，数量为 18、3、11、12、7、18、14、5、60，合计 148。正式输出未自动赋予 C2 等名称，也没有自动读取图例。电脑现有 Python/Pillow/NumPy/OpenCV 环境中，批量运行该图约 0.79 秒；这是单次诊断时间，不是 Android 性能或稳定基准，也未测峰值内存。

随后固定该脚本参数运行全部样例，不再根据验收组结果修改算法。18 张图纸中：

- S18 的网格与匿名颜色组数量通过上述核对，仅证明开发样例的这一部分。
- S01、S04、S06、S09、S10 输出了网格假设；主会话逐一查看叠线图，发现计入编号边框、错误间距或边缘漏检，均不算成功。
- 其余 12 张未找到可靠周期，明确保留失败；色卡 S00 也未返回可靠网格。

除 S18 外尚无逐格人工参考答案，本轮不能计算跨图纸逐色准确率。完整结果在 `/tmp/pindou-issue8/grid-batch/results.json`，脚本在 `/tmp/pindou-issue8/grid_probe_auto.py`，定位图在同批次目录；这组临时探针没有接入应用，不是 #8 的完整交付。

原图还证明两个实际边界：白豆和空白格可能同底色，需结合格内字迹；密集小格、近似色和水印会影响定位及分类。RGB 只能辅助同图分组，不能作为 MARD 色号真值。下一步建议先改进开发组的网格定位，再独立验证少量字母数字的色号识别；无需因此直接引入通用视觉模型。该建议尚未改变现行专项“图例优先、本体后备”的正式约定。

## Jev 到底是什么

TypeSafe 在 **2026-09-15** 发布 Jev，称其为 System One 模型。输入共享状态及多个问题，输出有限选项、等级评分、真假判断及相应分数，减少逐字生成回答的开销。这与“专门训练来读取图片字符”的 OCR 是两种职责。[官方发布](https://typesafe.ai/blog/introducing-system-one-models-and-jev)、[接口概念](https://docs.typesafe.ai/introduction)

当前官方模型 `jev-1.13.0` **只接收文字、文本 JSON 对象或数组，不支持图片、音频、视频**；非文字输入需要先处理成文本。官方文档提供托管 API，本次没有发现可下载权重或 Android/小程序本地运行入口。因此不能把它的云端响应速度当成手机离线性能，也不能从快和便宜推断模型参数少。[模型支持范围](https://docs.typesafe.ai/models)、[State](https://docs.typesafe.ai/concepts/state)、[API](https://docs.typesafe.ai/api)

官方“无幻觉”宣传中的技术保证主要涉及输出符合既定类型；其发布说明和已知问题页不能支持“答案一定正确”的解释。[发布说明的限制](https://typesafe.ai/blog/introducing-system-one-models-and-jev)、[已知问题](https://docs.typesafe.ai/model-jaggedness/jev-1.13)

| 项目 | 真实能力与运行方式 | 与本项目的距离 |
| --- | --- | --- |
| [Jev Visual](https://github.com/hr98w/jev-visual/blob/main/README.zh-CN.md) | Qwen3.5-0.8B + MLX；支持图片、候选打分和共享图片上下文；作者在 M4/16GB 上验证；下载约 **596 MiB** 权重 | 现成实现要求 Apple Silicon Mac，不是 Android 库；每题 2–26 个选项，不能直接一次覆盖 221 色；作者明确未复现 TypeSafe 私有训练或校准 |
| [Simple Jev](https://github.com/featherless-ai/simple-jev/blob/main/README.md) | Transformers/PyTorch 本地服务，可从 Qwen3.5-0.8B CPU 路径起步；读取候选标签分数，由代码组装结果 | **本次回读的开源 HF server README 明确仅支持文字**。其[演示站](https://simple-jev.featherless.ai/)宣称托管 Gemma/Qwen 支持图片，不能把托管能力等同于当前本地源码能力；无已核实的 Android/小程序版本 |
| [SemIf，原 OpenJev](https://github.com/TheoLeeCJ/SemIf/blob/master/README.md) | 开源有限选项判断；Python/CUDA、MLX 和浏览器 WebGPU 路径；2026-09-18 增加浏览器模型 | 已列浏览器下载约 639 MB、1.56 GB、3.01 GB；README 的验证以文字决策为主，不证明拼豆 OCR，也不证明微信小程序可运行 |

这些项目主要改变**怎么使用已有模型**，并不会自动把视觉模型缩成微型模型。候选分数也不能未经本任务校准就称作答案正确概率。Jev Visual 和 Simple Jev 的作者均明确说明了这一点。[Jev Visual 推理说明](https://github.com/hr98w/jev-visual/blob/main/docs/inference.md)、[Simple Jev README](https://github.com/featherless-ai/simple-jev/blob/main/README.md)

### Android 上能否实现类似做法

有可行的技术起点：阿里 MNN 提供完全在设备内运行的 Android 多模态应用，支持 Qwen3.5；官方模型目录有 **Qwen3.5-0.8B-MNN 约 548 MB**，包含语言和视觉文件。[MNN Android](https://github.com/alibaba/MNN/blob/master/apps/Android/MnnLlmChat/README.md)、[官方模型文件](https://huggingface.co/taobao-mnn/Qwen3.5-0.8B-MNN/tree/main)

**推断：** 可以研究在该视觉模型上直接给有限候选打分，移植 Jev 类用法。但“底层模型能在 Android 跑”不等于“现有 Jev Visual 的缓存、打分与批处理可以原样搬过去”。仍需实现并验证候选打分、图像分辨率、运行内存及与现有 uni-app 的连接。本次没有安装或运行它，不能承诺速度和准确率。MNN 的官方应用也明确指出其设备测试范围有限。

## 微信小程序：已有原生能力，但不能用浏览器成功代替

微信官方示例已包含“选择照片 → 读取像素 → `VKSession.runOCR`”的路径；官方类型定义标注静态图像 OCR 从基础库 2.27.0 起提供。本次没有运行用户微信，也没有验证目标手机断网、首次初始化、文字覆盖或识别效果。它值得在小程序阶段先测，可省去自行携带一套识字模型。[官方照片 OCR 代码](https://github.com/wechat-miniprogram/miniprogram-demo/blob/master/miniprogram/packageAPI/pages/ar/photo-ocr-detect/photo-ocr-detect.js)、[官方接口定义](https://github.com/wechat-miniprogram/api-typings/blob/master/types/wx/lib.wx.api.d.ts)

官方 `wx.createInferenceSession` 接口支持从本地路径加载 ONNX，基础库要求 2.30.0。**这是自带小模型的入口，不保证任意 ONNX 模型兼容。** PP-OCRv6 Tiny 还需检查模型算子、动态尺寸、前后处理和目标设备。类型定义中的 `allowNPU` 仅对 iOS 有效，不可据此承诺 Android 小程序 NPU 加速。上述微信开发者文档网页本次无法直接读取，结论以腾讯官方 GitHub 接口定义及示例源码为依据。

本次没有核实到可直接在微信小程序内运行的 Jev 类视觉模型成品。浏览器 WebGPU Demo、电脑本地网页、手机请求电脑 HTTP 服务，均不等于小程序本地推理。

## 对 Issue #8 的具体意义

当前 Issue #8 约定验证图例提取：自动定位图例、读取诸如 `C12 (3)` 的文字，再校验色号、数量、重复和完整性。该流程是现行任务约定，并非判断“数格子一定需要 OCR”的依据。现有 OpenCV 试验已从原图自动定位九个长条图例，包括 H7 末行；它尚未读取字符，不能算 Issue #8 通过。样例分组已在首次 OCR 前登记，本次没有实际运行 OCR。

**适合借鉴 Jev 的地方（推断，未实测）：** 将复杂识图拆成有限、可拒绝的判断，例如“这是图例/标题/水印”“这个格子是制作格/空白/未知”“两个相似色号候选哪一个更符合文字”。程序继续负责累计与数量校验。

**当前不适合直接替换的地方：** 官方 Jev 根本不接收图片；开源视觉仿实现仍要处理数百 MB 模型。任意数量也不是少量固定选项——若先靠 OCR 找出数字再交给 Jev 选择，就没有替代 OCR；若改成逐字符分类，则仍需开发一套识字流程。选项中必须有未知/不适用，不能强行把错误字符变成合法 MARD 编号。

下一步优先研究点阵计数及轻量色号对应。若最终调整主流程，需由用户确定方向后回填根规格和专项，不能用匿名颜色组替代 #8 要求的自动逐色结果。小 OCR 是需要时的比较候选；本次没有证据支持加入 Jev 类通用视觉模型。第 8 项仍以本地验证为范围。
