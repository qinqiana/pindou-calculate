## 0. 本票要回答的问题

对 ONNX Runtime（Android 包 / Mobile 精简包）、MNN、LiteRT（原 TensorFlow Lite）三家：接入方式与 `.so` 体积、最低 API、许可与维护状态；INT8/INT4 量化支持；Paddle/PyTorch 模型族到各运行时的导出链路成熟度；给出推荐与切换条件。JS bridge 接入不在本票范围。

## 1. 三家运行时基础事实

### 1.1 ONNX Runtime（Microsoft）

- **接入方式【事实】**：Maven Central 坐标 `com.microsoft.onnxruntime:onnxruntime-android`，`implementation` 一行引入；也提供 C/C++ 用法（解压 AAR 取 `jni` 下 `libonnxruntime.so`）。来源：[官方安装文档](https://onnxruntime.ai/docs/install/#install-on-android)、[Maven Central 目录](https://repo1.maven.org/maven2/com/microsoft/onnxruntime/onnxruntime-android/)。
- **版本与维护状态【事实】**：最新 1.30.0（2026-09-14 上架 Maven Central），2026 年内基本每月一版，维护活跃。来源：[Maven Central 版本列表](https://repo1.maven.org/maven2/com/microsoft/onnxruntime/onnxruntime-android/)。
- **许可【事实】**：MIT。来源：[microsoft/onnxruntime LICENSE](https://raw.githubusercontent.com/microsoft/onnxruntime/main/LICENSE)。
- **最低 Android API【事实】**：官方构建脚本注释写明"Android API 24 是 Android 构建的默认 target/min 版本，原生库默认对 NDK API 21 编译"。来源：[build_aar_package.py](https://github.com/microsoft/onnxruntime/blob/main/tools/ci_build/github/android/build_aar_package.py)。项目 minSdk 29 满足。
- **体积【事实】**：
  - 全量包 1.30.0 AAR 53,040,218 字节（约 50.6MB，含 arm64-v8a/armeabi-v7a/x86/x86_64 四个 ABI；本项目只出 arm64-v8a，实际进 APK 的只有其中一份）。来源：[Maven Central 1.30.0 文件列表](https://repo1.maven.org/maven2/com/microsoft/onnxruntime/onnxruntime-android/1.30.0/)。
  - 官方文档给出的体积对照（1.18.0）：预编译移动包 AAR 24,415,212 字节、其中 arm64-v8a `libonnxruntime.so` 解压后 16,276,832 字节（约 15.5MB）；按模型裁剪算子的自定义构建 AAR 7,532,309 字节、arm64 .so 3,962,832 字节（约 3.8MB）。来源：[Deploy on mobile 官方文档](https://onnxruntime.ai/docs/tutorials/mobile/)。
- **Mobile 精简包状态【事实】**：Maven Central 上 `onnxruntime-mobile` 预编译包停留在 1.18.0（2024-05-20），之后不再发布。来源：[Maven Central onnxruntime-mobile 目录](https://repo1.maven.org/maven2/com/microsoft/onnxruntime/onnxruntime-mobile/)。**【推断】**要精简体积需走官方"自定义构建"（按模型算子列表裁剪，`--minimal_build` + ORT 格式模型），构建链需要本机 NDK/编译环境。

### 1.2 MNN（阿里巴巴）

- **接入方式【事实】**：Maven Central 上的 `com.alibaba.android:mnn` 停留在 0.0.8（2021-02-24），**多年未更新，不可用**。来源：[Maven Central 目录](https://repo1.maven.org/maven2/com/alibaba/android/mnn/)。现行分发方式是 GitHub Releases 的压缩包（含 .so 与头文件）或源码编译，需手动放进 `jniLibs` 或本地 AAR。**【未核实】**3.6.1 发布 zip 内部是否带现成 AAR（未下载）。
- **版本与维护状态【事实】**：最新 3.6.1（2026-07-23），2026 年内约每月一版，维护活跃。来源：[alibaba/MNN Releases](https://github.com/alibaba/MNN/releases)。
- **许可【事实】**：Apache-2.0。来源：GitHub API 仓库许可字段（`gh api repos/alibaba/MNN/license` 返回 SPDX `Apache-2.0`）。
- **最低 Android API【事实】**：官方 Android 工程配置 `minSdkVersion 14`，ABI 含 `armeabi-v7a`、`arm64-v8a`。来源：[project/android/build.gradle](https://github.com/alibaba/MNN/blob/master/project/android/build.gradle)。项目 minSdk 29 满足。
- **体积【事实】**：3.6.1 发布的 `mnn_3.6.1_android_armv7_armv8_cpu_opencl_vulkan.zip` 为 6,197,903 字节（约 6.2MB），这是 **armv7+arm64 双 ABI、CPU+OpenCL+Vulkan 全后端**的整包大小。来源：[GitHub Releases 3.6.1 资产列表](https://github.com/alibaba/MNN/releases/tag/3.6.1)。**【推断】**本项目只出 arm64-v8a 且可只用 CPU 后端，实际进 APK 的 .so 明显小于 6.2MB（约一半或更少）；**【未核实】**精确大小需下载拆包实测。
- 注：官方文档站（mnn-docs.readthedocs.io）当前标注版本 2.1.1，落后于 3.6.1 发布版，个别参数以仓库源码为准。

### 1.3 LiteRT（Google，原 TensorFlow Lite）

- **接入方式【事实】**：发布在 **maven.google.com**（不是 Maven Central），坐标 `com.google.ai.edge.litert:litert`（及 `litert-gpu` 等）。来源：[官方迁移文档](https://developers.google.com/edge/litert/migration)。
- **版本与维护状态【事实】**：v2.2.0（2026-08-14，含 CompiledModel 新 API）；Interpreter 经典 API 线最新 v1.4.2（2026-03-16）。来源：[LiteRT for Android 官方版本表](https://developers.google.com/edge/litert/android)。
- **许可【事实】**：Apache-2.0。来源：GitHub API 仓库许可字段（`gh api repos/google-ai-edge/LiteRT/license` 返回 SPDX `Apache-2.0`）。
- **最低 Android API【事实】**：v2.x minSdk 23；v1.4.x minSdk 21。来源：同上官方版本表。项目 minSdk 29 满足。
- **体积【事实】**：官方"缩减二进制大小"文档给出**选择性构建**（只编进模型用到的算子）的 AAR 实测：MobileNet 图像分类模型 arm64-v8a AAR 仅 382,892 字节（约 374KB）；含 Select TF ops 的场景约 2.3MB。来源：[Reduce LiteRT binary size](https://developers.google.com/edge/litert/build/reduce_binary_size)。**【未核实】**maven.google.com 上 `litert` 全量 AAR 的精确大小（页面为 JS 渲染，未下载实测）。
- **【推断】**三家中最小包体，但需要 Bazel 选择性构建才能达到几百 KB；直接引全量 AAR 的体积未核实。

## 2. INT8 / INT4 量化支持

### 2.1 ONNX Runtime

- **INT8【事实】**：官方量化工具支持动态/静态 INT8（QOperator 与 QDQ 两种图表示），CPU 上支持 S8S8/U8S8/U8U8，CNN 推荐静态量化；Android 上可用 EP 为 CPU / NNAPI / XNNPACK。官方建议：**量化模型先用 CPU EP，未量化模型先上 XNNPACK**。来源：[Quantize ONNX models](https://onnxruntime.ai/docs/performance/model-optimizations/quantization.html)、[Deploy on mobile](https://onnxruntime.ai/docs/tutorials/mobile/)。
- **NNAPI 对 INT8 的支持【事实】**：NNAPI EP 要求 Android 8.1（API 27）+，推荐 9（API 28）+；支持算子表含 `QLinearConv`、`QLinearMatMul`、`QuantizeLinear/DequantizeLinear`（要求 scale/zero point 为常量）。来源：[NNAPI Execution Provider](https://onnxruntime.ai/docs/execution-providers/NNAPI-ExecutionProvider.html)。
- **INT4【事实】**：官方支持 INT4/UInt4 **仅权重的分块量化**，但只作用于 `MatMul`（转 MatMulNBits）与 `Gather`（转 GatherBlockQuantized）两类算子——面向 Transformer/LLM 场景。来源：[Quantize ONNX models - Quantize to Int4/UInt4](https://onnxruntime.ai/docs/performance/model-optimizations/quantization.html)。**【推断】**对本项目以 Conv 为主的检测器/分类器，ORT 的 INT4 路径基本不适用；INT8 才是 ORT 下的可用量化档。

### 2.2 MNN

- **INT8【事实】**：两条官方路径——(a) 离线量化 `quantized.out` / `mnnquant`，100~1000 张校准图，全图 int8 推理，官方示例 MobileNetV2 在 ARMv8 上 62ms→42ms；(b) 权重量化 `--weightQuantBits 2~8` + 编译 `MNN_LOW_MEMORY=ON` + 运行时 `Memory_Low` 开启动态量化（卷积等核心算子走 int8 计算）。来源：[MNN 模型压缩指南](https://mnn-docs.readthedocs.io/en/latest/tools/compress.html)。
- **INT4【事实】**：权重量化位宽官方支持 2~8bit（`--weightQuantBits`，覆盖 conv/matmul/LSTM 权值），并有 ARM CPU 低 bit GEMM kernel（W2/W3/W4/W8）。来源：[MNNConvert 参数说明](https://mnn-docs.readthedocs.io/en/latest/tools/convert.html)、[压缩指南](https://mnn-docs.readthedocs.io/en/latest/tools/compress.html)。**【推断】**三家当中，只有 MNN 对 **Conv 权重**有官方 INT4（乃至更低）存储量化路径；配合动态量化可实际提速。

### 2.3 LiteRT

- **INT8【事实】**：官方支持训练后全整数量化（权重+激活均 INT8，需代表性数据集校准），也有 16x8 变体。来源：[Post-training integer quantization](https://developers.google.com/edge/litert/conversion/tensorflow/quantization/post_training_integer_quant)。
- **INT4【事实】**：官方 `ai-edge-quantizer`（Apache-2.0，维护活跃）支持 INT4 权重（动态 WI4、静态 WI4+AI8/AI16、weight-only WI4、分块量化、GPTQ 等）。来源：[google-ai-edge/ai-edge-quantizer README](https://github.com/google-ai-edge/ai-edge-quantizer)。**【推断】**int4 权重量化在 LiteRT 上主要服务于 FullyConnected/MatMul 密集层与 LLM 场景，对 Conv 检测器的适用性需实测。

## 3. 导出/转换链路成熟度

### 3.1 Paddle → ONNX → ORT

- **【事实】**`paddle2onnx` 为 PaddlePaddle 官方工具（Apache-2.0，活跃维护），命令行一键导出 ONNX，opset 支持 7~19、可自动升 opset、带 onnx checker。来源：[Paddle2ONNX README](https://github.com/PaddlePaddle/Paddle2ONNX/blob/develop/README_en.md)。
- **【事实】**PaddleOCR 官方文档有专门的 paddle2onnx 部署章节（PP-OCR 检测/识别模型导出 ONNX 后跑 ORT）。来源：[PaddleOCR 官方文档](https://paddlepaddle.github.io/PaddleOCR/v2.9.1/en/ppocr/infer_deploy/paddle2onnx.html)。
- **【事实】**候选模型存在性：PaddleOCR 仓库（最新 v3.7.0，2026-06-11）内有 PP-OCRv5 mobile rec、PP-OCRv6 tiny/small det 与 tiny rec 的训练配置与文档。来源：[PaddleOCR Releases](https://github.com/PaddlePaddle/PaddleOCR/releases)、仓库 `configs/det/PP-OCRv6/`、`configs/rec/PP-OCRv5/`。**【未核实】**PP-OCRv6 是否已放出公开推理权重（未下载核实）。
- **成熟度判断【推断】**：这是三条链路里最成熟的一条——两端都是官方工具且有 PP-OCR 专项文档。

### 3.2 Paddle → ONNX → MNN（MNNConvert）

- **【事实】**MNNConvert 支持 ONNX / TFLite / TorchScript / Caffe / TF 转 MNN，并带官方正确性校验脚本（`testMNNFromOnnx.py` 等，可与 ONNXRuntime 输出逐层对比、二分定位错误层）。来源：[MNN 模型转换工具文档](https://mnn-docs.readthedocs.io/en/latest/tools/convert.html)。
- **【事实】**Paddle2ONNX README 明确把 MNN 列为 Paddle 模型的目标部署引擎之一。来源：同上 README。
- **【推断】**链路各环节都是官方工具，但 DBNet 检测头、SVTR/CRNN 识别模型转 MNN 的逐算子成功率没有官方承诺，必须用校验脚本实测。**【未核实】**本项目具体模型（短文本、字符集 A–Z/0–9/少量标点、动态宽度输入）的转换实测结果。

### 3.3 PyTorch → ONNX → ORT / MNN

- **【事实】**ORT 官方定位就是吃 ONNX；MNN 除 ONNX 外还可直接吃 TorchScript（`MNNConvert -f TORCH`，要求 `torch.jit` 导出的 .pt）。来源：[MNNConvert 文档](https://mnn-docs.readthedocs.io/en/latest/tools/convert.html)。
- **【推断】**torchvision 系（MobileNetV3、SSDLite）与自训 CRNN/SVTR-tiny 走 `torch.onnx.export` 是常规路径，成熟度不低于 3.1；RT-DETR 类含 transformer 解码的检测器导出后处理较复杂，建议导出时把 NMS/后处理留在模型外（Java/JS 侧），只导出骨干+头。

### 3.4 PyTorch / ONNX → LiteRT

- **【事实】**PyTorch → LiteRT 有 Google 官方 `litert-torch`（原 ai-edge-torch），基于 `torch.export()`，覆盖 Core ATen 算子，但 **PyTorch converter 目前标注为 Beta**（Generative API 为 Alpha）。来源：[google-ai-edge/litert-torch README](https://github.com/google-ai-edge/litert-torch)。
- **【事实】**ONNX → TFLite **没有 Google 官方转换器**；社区常用路径 ONNX→TF→TFLite 依赖第三方工具。**【未核实】**`onnx/onnx-tensorflow` 当前维护状态与转换质量（GitHub API 显示 2026-08 仍有提交，许可字段为 NOASSERTION）。
- **已知坑【事实+推断】**：LiteRT 内建算子只是 TF 算子子集（见[算子兼容文档](https://developers.google.com/edge/litert/conversion/tensorflow/ops_compatibility)），缺算子要引 Select TF ops（体积涨约 2MB，见选择性构建表）或写自定义算子。**【推断】**DBNet 后处理（阈值图→多边形展开）与 CTC 解码不适合放进模型图，应在导出时切到模型外用 Java/JS 实现——这也与本项目"配对与加总由代码做"的既定架构一致；动态尺寸输入在 LiteRT 上需靠 resize input 或固定多档尺寸，比 ONNX/MNN 的动态 shape 支持麻烦。
- **成熟度判断【推断】**：对 Paddle 系模型，Paddle→ONNX→（第三方）→TFLite 链路最弱；对 PyTorch 系可试 litert-torch，但 Beta 状态 + 算子覆盖风险使它不适合做首选。

## 4. 推荐结论

**推荐：首选 MNN + MNN 模型格式（导出链路：Paddle/PyTorch → ONNX → MNNConvert → .mnn），备选 ONNX Runtime（导出 .onnx，必要时 ORT 格式 + 自定义裁剪构建）。**

理由：

1. **可用性不被"阿里系优先"牺牲【推断】**：MNN Apache-2.0、minSdk 14、2026 年持续月更、Android 全后端双 ABI 整包仅 6.2MB（arm64 CPU-only 会更小），是唯一在**不切算子自定义构建**的前提下就能把运行时压进个位数 MB 的方案；INT8 离线量化、2–8bit 权重压缩（含 Conv 的 int4 权重存储）都有官方工具与文档。
2. **链路成熟度可接受【推断】**：Paddle→ONNX（官方）→MNN（官方 + 逐层校验脚本）每一环都有官方工具；风险集中在"本项目具体模型转 MNN 的算子覆盖"，可用 `testMNNFromOnnx.py` 在训练出第一个学生模型当天就验证。
3. **ORT 作为保底【推断】**：生态与文档最成熟、Maven 直引、PP-OCR 有官方 ONNX 部署文档；代价是体积——全量包 arm64 .so 约 15.5MB（1.18.0 官方数字），要达到约 4MB 需自定义裁剪构建（增加一条 NDK 编译链维护成本）。Maven 预编译 mobile 精简包已停更（停在 1.18.0）。
4. **LiteRT 不建议首选【推断】**：体积最小（选择性构建约 0.4MB 级），但 Paddle→LiteRT 无官方链路、PyTorch→LiteRT 仍是 Beta，转换风险最高；除非包体压力极端化，不优先。

**切换条件（触发即重评）**：

- 若 MNNConvert 对选定的检测器/识别器模型出现**无法绕过的缺失算子或精度校验不通过** → 切换到 ONNX Runtime（先全量包跑通，再做自定义裁剪构建压体积）。
- 若 MNN 全图 int8 量化后字符识别准确率掉到不可用 → 退回 MNN 权重量化 8bit + FP16 运行时，或换 ORT INT8 QDQ 对比。
- 若 50MB 探索目标必须压到极低且模型族收敛到 PyTorch 系 → 再评估 litert-torch（Beta）+ LiteRT 选择性构建。

**给训练侧的导出要求【推断】**：训练导出时把 DBNet 后处理、CTC 解码、NMS 等一律留在模型图之外（Java/JS 实现），模型只出"张量进、张量出"的骨干+头；识别器按固定输入高度 + 动态宽度（或多档固定宽度）设计，三种运行时都更容易消化。

## 5. 未核实事项汇总

1. MNN 3.6.1 Android 包内 **arm64-only、CPU-only 的 .so 精确大小**（本次未下载拆包；6.2MB 是双 ABI+全后端 zip 的上界）。
2. LiteRT `com.google.ai.edge.litert:litert` 全量 AAR 的精确大小（maven.google.com 页面 JS 渲染，未下载实测）。
3. ORT 1.30.0 全量 AAR 内 arm64 `libonnxruntime.so` 的解压大小（官方表格只给了 1.18.0 的 15.5MB 数字）。
4. PP-OCRv6（tiny/small det、tiny rec）是否已发布公开推理权重；PP-OCRv5 mobile 的 ONNX/MNN 转换实测成功率。
5. 本项目候选模型（DBNet、SVTR/CRNN、PicoDet、自训分类器）经 MNNConvert / litert-torch 的逐算子转换与精度校验结果——需等训练出第一个学生模型后实测。
6. ORT 预编译 AAR manifest 中的实际 minSdk 值（源码注释称默认 24，未直接读 AAR manifest 核实）。
7. `onnx/onnx-tensorflow` 的当前维护质量（API 显示未归档、2026-08 有提交，但许可字段 NOASSERTION，未评估转换正确性）。
