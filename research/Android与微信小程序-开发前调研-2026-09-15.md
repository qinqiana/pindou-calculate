# Android 与微信小程序：开发前调研（2026-09-15）

探索：Luna，max 推理强度。主会话在结论返回后回读来源并补充第 10 节；涉及被纠正的推断，以第 10 节及当前根规格的确认状态为准。本文保留调研当时的候选与未决状态，后续用户已授权发布根规格与配置；当前产品与技术决定以 SPEC.md 为准。

## 说明与结论边界

本报告只做开发前调研，不替代产品、架构或最终验收决定。外部事实以一手官方文档为主，均标注查阅日期；“建议/推断”来自这些事实与当前样例，不是已确认需求；“未核实”不能写成支持承诺。第三方报告仅作为竞品名称线索，未抄录其中的个人信息、过时星数或没有一手链接的结论。

产品边界是：第一阶段用真实 Android 安装包验证完整的库存、图纸用量、离线记账、备份恢复和分享闭环；之后再接续微信小程序。首版只接收 PNG/JPG 图纸，OCR 只在用户主动发起时上传当次截图；首版不接真实广告、支付。本轮调研不调用收费识别服务，但这不是产品永久禁用收费 OCR 的要求。分享图片本地生成、先预览及默认不带库存余额和历史属于方案建议；不操作用户微信界面。

**阶段性结论**：

1. 候选中，**uni-app Vue3/TypeScript 暂列首选候选**，因为官方明确覆盖 Android App 与微信小程序，且可用条件编译保留少量平台适配。uni CLI 不能直接云打 APK，HBuilderX 文档写暂不支持 Linux；但不能据此排除 Android 离线 SDK/Gradle 构建，主会话在第 10 节补入这一遗漏路线。所有路线仍待可安装 APK 的实际验证。
2. **uni-app x 暂列备选**：Android 侧更接近原生 Kotlin/UTS，官方已提供微信小程序编译路径，但 API、布局和组件差异需要逐项核对，不能因为“同一工程”就假定业务层完全复用。
3. **Taro + React Native** 也有 Android 和微信小程序路径，可共享部分代码，但需处理 RN shell 和平台适配；不能与“React Native 单独使用、Flutter 未列官方微信目标”混为同一结论。没有既有 React/Dart 项目的事实，不等于已经知道开发者不熟悉这些框架。
4. Luna 提出 **Android 端 ML Kit 或 PaddleOCR 移动端模型 + 确定性解析器**作为候选。主会话复核：这不是原已确认在线识别方案的自动替代，应列入开发者问卷。在线服务仍需补齐删除证据；本地识别、云端识别和手工输入均不能在未测原样例时冒充 9 色 148 颗自动通过。
5. 小红书分享应默认按用户指定的**“全屏图”功能**设计。公开一手资料目前没有该功能当前的比例、像素、文件格式或安全区规范；旧版分享 SDK 规则不能直接替代它。3:5、1080×1800 只能作为待真机验证候选，不能当官方规格；此前 3:4 建议撤销。第一阶段可靠交付是本地生成、预览、保存相册和系统分享。

## 1. 当前输入与必须保留的验收事实

项目需求书规定 MARD 221 色号、库存非负整数、批量写入全成全败、制作扣减可撤回、全量备份先预览再整体替换，以及图例识别结果必须人工确认后才进入库存计算，详见[需求书-拼豆库存与图纸消耗-v1.0.md](../需求书-拼豆库存与图纸消耗-v1.0.md)和[项目词汇与上下文](../CONTEXT.md)。这些业务规则不能因框架的本地存储 API 方便而改变。

本地样例的静态事实（2026-09-15 实测文件）：

- [148 颗 PNG 样例](../参考样例/豆画-Mard-148图纸样例.png)是 5000×3820，约 19.1MP；底部图例是两行，H7 单独在第二行。
- 需求书中的期望逐色结果为 C2=18、C12=3、C16=11、C17=12、C19=7、C29=18、H2=14、H3=5、H7=60，9 色合计 148。漏一个色号、代码错、数量错或只输出部分结果，都不能算自动识别通过。
- [补充长图样例](../参考样例/参考图纸/1789460476075_0dbf7801-f253-4f79-8001-c0def766910f_2011655912785230796_1080x2596.webp)为 1080×2596，图例有三行并带小红书水印；WebP 只作为调研输入观察，首版 PNG/JPG 边界不扩展到 WebP。

因此，识别裁切不能用“图片底部固定百分比”，预处理也不能按普通手机小图设计；Android 实机至少要覆盖 19.1MP 原图、两行图例、三行图例和水印干扰下的内存、耗时、旋转与保存结果。

### 2.2 离线存储、事务与完整备份

平台键值存储可以存偏好和小状态，但不等同于库存账本事务：

- [uni-app 存储文档](https://uniapp.dcloud.net.cn/api/storage/storage?id=storage)（更新 2025-08-01，查阅 2026-09-15）与 [uni-app x 存储文档](https://doc.dcloud.net.cn/uni-app-x/api/storage.html)说明微信小程序单 key 约 1MB、总量约 10MB，数据为 JSON 可序列化；uni-app x Android 的实现落在应用 SQLite，但文档没有给出跨多 key 的业务事务 API。
- 同一文档说明 App 可用 SQLite/文件能力；[uni.chooseFile](https://uniapp.dcloud.net.cn/api/media/file)在 App 可用、微信小程序不可用，微信需要 `wx.chooseMessageFile` 等平台 API。临时文件若要长期使用需要保存到持久路径。
- [Taro setStorage 文档](https://docs.taro.zone/docs/apis/storage/setStorage)同样是键值存储，并沿用小程序 1MB/10MB 限制；它不能自动提供库存余额、流水和制作记录的原子提交。

**工程建议（待主会话确认）**：Android 首版应选择有真实事务能力的本地数据库或等价单文件提交策略，把余额更新、逐色流水、制作记录和幂等请求标识放入同一提交边界；纯业务包保持 TypeScript/JSON 可移植。微信小程序不应直接假设能打开 Android 数据库，后续通过版本化完整备份接续。备份应包含 221 色资料来源、库存余额及估算标记、确认用量、制作快照、库存/撤回/更正历史和缩略图；原始大图不在备份中。导入要先校验、显示差异，再整体替换或取消，失败保留原数据。

**图片与完整备份的跨端边界**：图片选择/预览可以优先走 `uni.chooseImage`/`chooseMedia`，Android 临时路径需要按[文件 API](https://uniapp.dcloud.net.cn/api/media/file)保存；图片导出可走 `uni.saveImageToPhotosAlbum`，系统分享可走 `uni.shareWithSystem`。完整备份是任意文件的导入/导出，不能把“保存一张图片到相册”当成它的替代：App 侧要验证系统文件选择器、应用沙盒和用户可取出的导出路径，微信侧要验证 `wx.chooseMessageFile`、`wx.getFileSystemManager` 和当前可用的用户分享/保存路径。跨端 API 文档没有给出一个可直接承诺的“完整备份文件导出”按钮，因此文件适配器和真机门槛必须保留。

**备份文件候选（未定架构）**：可选用公开的 UTF-8、带格式版本的 JSON 合同，缩略图以独立文件/归档条目保存；应在 Android 与微信开发者工具中验证大文件、缩略图、中文标题、重复 ID、损坏文件和中断写入。微信小程序 API 的直接页面本轮无法稳定抓取，官方入口可复核：[wx.getFileSystemManager](https://developers.weixin.qq.com/miniprogram/dev/api/file/wx.getFileSystemManager.html)、[wx.chooseMessageFile](https://developers.weixin.qq.com/miniprogram/dev/api/file/wx.chooseMessageFile.html)、[wx.setStorageSync](https://developers.weixin.qq.com/miniprogram/dev/api/storage/wx.setStorageSync.html)；这些链接在真正开发前必须用当前微信开发者工具和真机验证，不能只凭跨端框架声明。

### 2.3 Linux 构建限制

- [DCloud CLI 文档](https://uniapp.dcloud.net.cn/worktile/CLI.html)（查阅 2026-09-15）明确：App 平台的 `uni cli` 只能生成离线 `wgt` 资源，不能直接云打 APK/IPA；HBuilderX CLI 可做 App 云打包，但同页明确写着 **HBuilderX 暂不支持 Linux**。因此“Linux 能运行 Node”不等于“Linux 能生成可安装 APK”。
- [uni-app App 运行文档](https://uniapp.dcloud.net.cn/tutorial/run/run-app)说明自定义基座和正式发布依赖 HBuilderX/正常打包流程；[App 环境文档](https://uniapp.dcloud.net.cn/tutorial/app-env.html)还给出当前云打包 Android 工具链版本。版本会变，实际打包必须记录所用 HBuilderX、Android SDK、JDK 和签名配置。
- Flutter 官方明确支持 Linux 主机开发 Android；Taro/RN 也可沿 Android 工具链运行，但这些方案仍不能解决微信小程序的独立构建、调试和双端验收。微信开发者工具当前机器/版本支持本轮未取得稳定的一手页面证据，不能承诺 Linux 原生可用。
- 本工作区本轮只做 PATH 轻量核对：能看到 `node`、`npm`、`java`，未看到 `adb`、`gradle`、`flutter`、`HBuilderX` 命令；这不等于整机不存在这些程序，也不构成构建链已验证的证据。

**实机门槛（建议）**：验证选定的 Android 离线 SDK/Gradle、非 Linux HBuilderX 或获准远程构建路径能取得可安装 APK；真实 Android 机检查数据库、19.1MP PNG、事务、备份和本地分享图片。微信先做文件合同可行性小验证，完整迁移验收留到小程序阶段；不把开发两个完整端作为自用 Android 交付前提。网页预览不能代替原生能力证据。

### 3.2 建议的识别管线（方案建议，不是已确定架构）

1. 图片选择后本地预览；不固定裁底部百分比。先用边缘、文字块坐标和版式候选定位图例区域，保留多行；对 19.1MP 图片做有界缩放/压缩，同时检查字符像素尺寸。ML Kit 官方建议字符高度约 16 px 以上，超过约 24 px 通常不再获得明显准确率收益，详见[输入图像指导](https://developers.google.com/ml-kit/vision/text-recognition/v2)。
2. OCR 仅输出候选文字、坐标、置信度和模型版本。随后由确定性解析器做 Unicode 空白/标点归一、受限的 `O/0` 等混淆修正，再匹配 MARD 221 白名单；未知代码进入“被拒绝识别项”，不猜颜色。
3. 解析器只接受类似 `C2 18`、`C2:18` 的有界格式，并保留 `rawText`、`bbox`、`confidence`、解析器版本和来源图片信息。重复色号如何合并、低置信度阈值和跨行配对需在验收前固定，不可由界面默默合并。
4. 建议结构化结果如下，字段名可调整但语义要稳定：

   ```json
   {
     "status": "complete | partial | failed",
     "items": [{"code":"C2","count":18,"rawText":"C2 18","confidence":0.98,"bbox":[0,0,1,1]}],
     "rejected": [{"rawText":"X9 4","reason":"not_mard221"}],
     "titleTotal": 148,
     "parsedTotal": 148,
     "parserVersion": "...",
     "provider": "on_device",
     "modelVersion": "..."
   }
   ```

5. 9 色 148 颗样例的自动验收必须逐项比对 9 个代码、9 个数量、总和 148，并在真实 Android 设备上跑原 PNG。任何漏项、错项或错误总和都失败；原需求没有把服务自报低置信度本身定义为数量正确时仍失败。用户后续手工修正不能冒充自动识别通过。补充三行样例可作版式回归，不改变首版 PNG/JPG 边界。

### 3.3 上传、密钥和删除证据

若采用首版在线 OCR 或后续多模态候选，建议仅保留一个后端代理接口：客户端传当次截图和必要的版本信息，服务端校验 PNG/JPG、像素/体积、限流和请求幂等；密钥只在服务端；返回统一结构化结果；临时截图、请求图像、日志中截图内容、对象存储、缓存及备份须核查是否留存。隐私验收至少需要：

- 能证明没有把库存、历史、原始大图目录或整相册一起上传；
- 能核验服务端临时文件和日志删除时间，而不是只看代码中的 `delete`；
- 能核验第三方服务的留存、备份、模型训练和人工审查规则；
- 删除无法核验时，该在线服务按本项目规则**不算通过**。单次使用可走手工兜底，但完整首版的自动识别要求仍未完成；如要改成本地 OCR，交开发者提出方案并由产品负责人确认。

## 5. 分享模板、全屏图和平台差异

### 5.1 Android 与微信的共同可靠路径

- [uni.saveImageToPhotosAlbum](https://uniapp.dcloud.net.cn/api/media/image)（查阅 2026-09-15）支持 App 和微信小程序保存本地/临时图片到相册，需处理用户权限和微信隐私协议；网络地址不能直接当本地文件使用。
- [uni.shareWithSystem](https://doc.dcloud.net.cn/uni-app-x/api/share-with-system.html)（查阅 2026-09-15）支持 App Android/iOS/Harmony 的本地图片系统分享。官方说明 Android 单图可进入朋友圈等用户选择的目标；多图发朋友圈需要微信 SDK，不能把系统分享当成平台直发成功。
- 朋友圈模板的 **1:1 是产品设计建议**，不是强制平台规范；建议先生成方图、预览、保存相册，再由用户选择系统分享目标。小程序 `onShareTimeline` 的官方参数说明见[小红书小程序页面分享文档](https://miniapp.xiaohongshu.com/doc/DC974753)：其 `imageUrl` 支持 PNG/JPG、显示长宽比 1:1，但这是小红书小程序的朋友圈/时间线分享卡片，不是微信朋友圈静态图片的全屏图规范，也不是本项目小红书全屏图规格。

### 5.2 小红书全屏图：当前可证实与不能承诺

**能证实的官方资料**：

- [小红书 Android 分享 SDK 文档](https://agora.xiaohongshu.com/doc/android)（更新 2023-10-11）说明图文笔记图片为 1–18 张，需要 AppKey、包名和 FileProvider；本地图片、URI 或网络图片均有接口路径。
- [小红书 iOS 分享 SDK 文档](https://agora.xiaohongshu.com/doc/ios)（更新 2023-11-16）描述旧裁剪规则：最长边超过 1920 会裁、宽度小于 600 会裁、宽高比小于 3:4 或大于 2:1 会裁、宽度超过 1280 会裁，同时注明 `imageId` 使用新规则；[官方 Q&A](https://agora.xiaohongshu.com/doc/qa)（更新 2023-12-10）也提示旧规则与新规则不同。
- [分享开放平台首页](https://agora.xiaohongshu.com/index)当前检索结果显示“暂停接入”（查阅 2026-09-15）。即便旧 SDK 文档存在，也不能承诺新应用现在可以取得 AppKey 或直接发布。

**未找到的官方证据**：本轮没有找到当前“全屏图”功能关于比例、像素尺寸、PNG/JPG/质量限制、底部/顶部 UI 遮挡、安全区或不同 Android/iOS 版本行为的一手公开规格。因此不能把 9:16 视频封面、广告素材、普通 3:4 笔记封面或小程序分享卡片规范移植成全屏图规范。

**仅作线索的非官方资料**：2025-10-06 的[开源项目 issue](https://github.com/Yeban8090/note-to-red/issues/32)记录用户使用小红书长文编辑器发布全屏图并认为比例约为 3:5；工具作者页面[Photix](https://crop.photix.cc/)也把“小红书竖屏全屏”标为 3:5，但页面同时提示预览仅供参考。两者都不是小红书官方规范，不能证明 3:5 或 1080×1800（3:5）是平台强制尺寸。

**首版建议（待用户/主会话确认）**：保留两套固定模板方向：

1. 朋友圈：1:1 产品建议画幅，图纸缩略图、标题、已确认总颗数/用色数和准备/完成状态，生成后预览。
2. 小红书：按“全屏图”模板接口生成，默认参数先做成可配置候选；在平台规格未确认前，不锁定 3:5/1080×1800，也不退回 3:4。必须把候选比例、像素、压缩格式先在用户实际 Android 设备的当前小红书发布预览中检查，后续发行再扩展兼容性设备，特别观察首屏裁切、底部工具条/评论区域遮挡、顶部状态区、长标题换行和水印位置。若官方规格仍不可取得，产品应显示“已生成图片，请在小红书预览确认”，保存相册与系统分享可分别验收，但全屏适配还必须通过真实裁切和遮挡检查，不宣称已自动发布。

两套模板都只允许固定排版，不扩成编辑器、模板商城或自动发帖。分享默认不含库存余额、缺口、估算标记、制作历史、本地路径和内部 ID；仅展示用户确认过的图纸标题、缩略图、总用量/用色数和真实状态。小红书 SDK 只有在“开放平台恢复接入、取得 AppKey、包名/FileProvider 配置、实机分享回调”全部成立后才可作为可选适配器；目前不锁 SDK。

## 6. 广告、买断与虚拟支付能力边界

首版不接真实广告和支付，但数据和产品边界不应把未来权益写死：

- 微信小程序广告：需要当前微信平台的资格、广告位及实际填充验证，不能承诺固定开通门槛。主会话复核发现，原引用 product/1219 的激励视频资料属于腾讯云超级应用服务（TCMPP），不是微信广告资格的直接证明；原 product/1301 页面本轮未能回读，不据此确认准入。接口存在与项目能开通必须分开。
- Android 买断若未来以 Google Play 分发， [Google Play 一次性产品/计费政策](https://support.google.com/googleplay/android-developer/answer/10281818?hl=en)和[计费集成文档](https://developer.android.com/google/play/billing/integrate)要求数字商品走 Play Billing，并在服务端验证购买、授予权益和确认订单；自用侧载 APK 不应先假设拥有 Play 购买链路。
- 微信支付需认证小程序及商户主体。[微信支付官方小程序支付准入](https://pay.wechatpay.cn/doc/v3/merchant/4015459512)（更新 2026-05-19）列出个体工商户、企业、事业单位、政府和社会组织等主体，个人主体不在该支持列表；还需商户号、AppID 绑定和相应支付权限。自用个人小程序不能承诺买断支付。
- 微信虚拟支付属于另一个平台能力和资格路径。DCloud 的[虚拟支付封装说明](https://github.com/dcloudio/uni-app/blob/uni-app-x/docs/api/virtual-payment.md)只说明部分平台 API 映射，不能代替微信资格/开通。当前只保留 `Entitlement/PaymentAdapter` 能力边界，首版不接 SDK、不接真实订单、不设计虚拟币。

### 10.1 纠正构建与复用推断

- **事实**：[DCloud CLI 文档](https://uniapp.dcloud.net.cn/worktile/CLI.html)确实区分 uni CLI 的资源构建与 HBuilderX 的云打包；[App 离线 SDK 官方说明](https://nativesupport.dcloud.net.cn/AppDocs/)则明确支持在本地原生环境生成安装包，并需申请 AppKey。[Android 官方命令行构建说明](https://developer.android.com/build/building-cmdline)提供 Linux 的 Gradle 构建路径。
- **推断，尚未跑通**：存在“Linux 生成 uni-app 资源 → App 离线 SDK 原生工程 → Gradle 打 APK”的候选组合。不能由 HBuilderX 不支持 Linux 推导“必须另有 Windows/macOS”；也不能由这几个文档推导本仓库已能打包。SDK、编译资源、AppKey 和原生模块的一致性仍由最小构建验证。
- **Taro 修正**：[官方 RN 文档](https://docs.taro.zone/docs/react-native)与其小程序目标支持代码复用，但须适配运行时。没有“同一运行时”并不是否定复用的充分理由；uni-app 的两端也不是同一运行时。框架推荐应结合开发者实际经验，而非自行假定经验。

### 10.2 补上事务能力的具体依据

[HTML5+ SQLite 官方 API](https://www.html5plus.org/doc/zh_cn/sqlite.html)提供 begin、commit、rollback。若采用传统 uni-app App 运行时，可把它作为 Android 事务候选；小程序不能直接调用该原生能力。框架的键值存储底层即使是 SQLite，也不等于业务获得跨多键事务。

据此建议：共享纯业务规则和版本化备份合同，Android 使用真实事务库存存储；微信未来另适配持久化能力，不强行共享同一个数据库 API。备份须取同一一致快照，恢复先在隔离区域校验，再整体切换；具体格式仍是待确认合同。

### 10.3 OCR 不擅自改范围或来源

原需求已确认在线图例识别和处理后删除。本轮禁止付费调用只是执行边界，不是产品规则。Luna 的端侧 ML Kit/PaddleOCR 候选可能有隐私好处，也增加原生集成、模型分发与微信复用差异，需开发者提案和负责人确认。不能自行以本地 OCR 替代在线方案，也不能把只有手工兜底称作完整首版。

现阶段应先明确统一的识别候选合同，评估可核验删除的在线提供方；如候选不满足，提问是否采用自管在线 OCR 服务或接受端侧替代。没有已选定的供应商，没有真实准确率、删除或成本测量。不把 SDK 隐私说明当作不同云 API 的政策，不把“不用于训练”等同于“处理后删除”。

解析也不能为了方便静默把未知色号改成另一个有效色号。安全归一化可处理空白与大小写；字母/数字混淆更正需保留原文和候选并给人核对。引擎自报“完整”或合计恰好相等均无法证明没有漏行；不确定完整性时保留待核对说明。

### 10.4 小红书全屏图与分享证据

主会话独立回读了 [2025-10-06 的使用反馈](https://github.com/Yeban8090/note-to-red/issues/32)与[Photix 作者页面](https://crop.photix.cc/)。二者提供 3:5 的线索，均不构成官方规范。1080×1800 只是符合该比例的可验证候选尺寸，安全区、格式、压缩质量和是否需要特定发布模式尚无实机证据。

[小红书分享平台官网](https://agora.xiaohongshu.com/index)的可检索页面显示“暂停接入”；直接回读一度失败，因此只记录公开检索状态，不宣称已测试新申请。传统 uni-app 的系统分享依据补为[对应的分享文档](https://uniapp.dcloud.net.cn/api/plugins/share)，不能只拿 uni-app x 文档替它证明能力。

“图片保存成功”不是“全屏图适配验收通过”。草稿必须同时保留保存图片的基本能力与小红书真实全屏预览不错误裁切、遮挡的验收门槛。分享所用确认版本与制作记录版本也要对应，旧版本拼过不能把修改后的新版本标成已完成。

### 10.5 商业化与资料权限

腾讯云超级应用服务、微信小程序、小红书小程序的同名 API 不能互相当作能力证明。微信普通支付准入也不能证明工具买断对应的虚拟支付能开通；本轮读取[微信虚拟支付官方入口](https://developers.weixin.qq.com/miniprogram/dev/api/open-api/payment/wx.requestVirtualPayment.html)未取得正文，相关资格保持未核实。广告、买断仅写独立能力边界，实际 SDK、主体、审核和权益由后续发行阶段复核。

第三方报告建议的多仓、会员、强制备份和制图引擎不自动成为需求。旧色值调研中“只显示色号”的文字已被后续用户决议明确替代，无需再问；当前有效规则是“允许社区版参考色且明确标注”。对真正未决的架构/产品事项，形成[开发者确认问卷](../to-questionnaire-root-spec.md)，不实施、不公开发布。

### 10.6 用户后续确认的开发设备

用户在主会话复核后明确已有 Android 和 Windows 开发设备，能接受 Linux 编译限制。根 spec 因而建议优先使用 Linux 日常开发、Windows 打包、Android 真机验收的候选路径；不将纯 Linux APK 构建作为阻塞，不为此额外搭建离线 SDK 工程。是否采用 uni-app 仍待开发者评审，设备可用不等于框架已经确定。
